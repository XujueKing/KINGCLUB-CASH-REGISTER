# 上菜确认与原请求恢复 UI（未营业验收）

订单商品行在 orders.serve 权限、open/clearing 场次、已知剩余数量大于零且付款条件可候选时提供确认入口。先付须 paid，员工后付允许 pending；这只是 UI 候选，后端仍核对实际归属、库存证据和权限，不信任界面判断。

员工填写“本次实际已上数量”，1 至记录剩余量的严格整数；空、零、负数、小数、超量都不能确认。确认说明明确这不是下单/出库/收款。客户端用观察的累计数和本次数量构造目标累计数，复用已测试的日志与控制器先保存后调用1919。成功后重新查1905，不乐观改数量。

同订单商品已存在本员工未决请求时，进入恢复而不是生成新 UUID。网络/业务失败发生在尝试提交之后也转恢复，不假定服务器失败。门店工作台和订单页均有“上菜请求处理”入口，便于退出订单或重启后找到原记录。

恢复页仅加载本人本设备记录；查询默认只读1920。not_observed 显示保留原记录，才提供显式“恢复原登记”。再次确认说明不再交付实物、不得因他人已登记或数量冲突新建替代请求；控制器仍先查询再决定是否重发原1919。未知/冲突无自动删除或取消入口。

同一界面操作中禁用其他操作，身份/场次/revision变化与离开前台会关闭未发送的确认框，迟到响应不切入新身份恢复页。等待人工确认时不显示网络加载条；回到前台重新拉取，不从旧缓存恢复成功状态。
