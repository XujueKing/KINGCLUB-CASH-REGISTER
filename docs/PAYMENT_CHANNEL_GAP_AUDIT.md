## 当前事实

| --- | --- | --- |
| 现金 | `cashier-runtime.ts` 的 1915 强制 channel=cash；1916/1917/1918 分别确认、查回、终止；有独立确认回执 | 真实员工/设备营业验收、交班对账；代码存在不代表启用 |

| 支付宝 | `routine-alipay-service.ts` 与 `alipay-app.ts` 生成 alipay.trade.app.pay 签名串，并有验签、查单、关单实现 | POS 收款对应适配、员工订单流程及原请求恢复；APP 签名串不是 POS 收款二维码或用户付款码处理器 |
| 会员余额 | 收银权限与准入枚举含 payment.balance/member_balance；`cashier-payment-intent.ts` 明确不扣钱包 | 会员支付授权、资产账本复用核查、原子扣款/回执/退款及对账。不能因收银模块未实现就声称全服务没有资产表 |
| 四渠道原请求查询 | 1923 路由到 CashierPaymentIntentService.lookup；客户端 PaymentAdmissionResult 只解释内部准入状态 | 非现金创建、持久化、渠道查询与恢复 UI；内部 confirmed/closed 不是独立渠道到账/关单证据 |

`cashier-session-scope.ts` 仅允许登记的员工接口 ID + adapter + session 策略匹配；会员支付执行器不能靠修改请求中的 app code 被收银员工复用。应保留此用途隔离，在统一后端内部增加正确的员工编排，不另建商务后端。

## 容易遗漏的生产闭环

`table-clear-plan.ts` 对收银来源订单只接受严格现金凭证；非现金分支明确拒绝 cashier origin/intents，目前支持的是会员先付渠道订单。新增 POS 支付时，必须同时补清台的渠道回执/账本核对，不能仅接一个“支付成功”按钮。也不能简单去掉 current.origin 检查，否则没有结算证据的收银单可能被清台。

## 后续实施顺序

1. 收银原请求与渠道流水持久化：门店、员工、设备、原订单、金额、币种、渠道固定；付款码只作短期敏感输入，不进入日志或离线草稿。未决请求先查回，不自动换号重收。
2. 根据已确认的扫码方向和实际开通产品选择官方 POS 适配；复用已有签名/验签与商户映射基础，但逐项核对产品契约。当前尚未补齐用户所说“部分已开通”的具体应用/门店权限信息。
3. 统一后端内部实现员工订单支付绑定、异步回调/主动查单、库存与支付账本事务；会员余额另加本人支付授权，不把入座或员工权限当作扣款授权。
4. 更新清台验证、超时恢复、退款/撤销和交班对账，再接四语言 UI；每条成功链与拒绝/并发/响应丢失链分别验证。
5. 官方沙箱、隔离集成、真机与明确金额的真实交易验收分别记录；部署、迁移、真实交易均另行确认范围。

本计划不删减美团/抖音官方团购核销及其转 APP 券/订单抵扣双模式；它们不应冒充微信/支付宝支付渠道，仍需独立核销回执与防重复发券/抵扣链。
