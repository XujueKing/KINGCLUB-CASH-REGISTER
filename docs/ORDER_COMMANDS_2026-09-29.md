# 员工下单命令与恢复控制器

本节点接入统一后端188定义的1912提交、1913查回、1914终止；仅客户端模型、加密持久记录和控制器，尚未把会员选择/目录页面连接成真实购物车与恢复页面。没有发起真实业务请求，服务端元数据及新提交开关仍默认关闭。

## 命令和归属

PendingOrder.prepare 要求有效员工会话、orders.create、本门店场次上下文与该页真实可用入座会员、CNY、有效商品观察数量。商品列表不可重复，最多50项，每项1–1000件，总额最多100000000分。仍由服务端最终核价和判断库存、入座与权限；客户端选择会员不代表扣钱包授权。

原命令使用操作系统安全随机UUID，锁定门店/桌台/场次/消费会员/付款模式/商品版本和价格。按商品编号排序，映射及列表深度不可变。原请求一经准备与持久化，重试不得重新生成UUID或使用当前购物车替换内容。

## 保存与恢复

- OrderJournal 使用既有平台加密存储、独立 pending_staff_orders_v1 键；不保存API密钥、刷新令牌、会员姓名或手机号。地址/员工/设备/门店绑定，退出登录不清除订单记录。
- 发送前必须完成写入并读回精确比对；没有明文或内存替代路径。损坏/未知版本/读取失败不清理记录。写入后报错仍可重新加载原记录。
- 同一应用isolate跨实例串行写入，最多100个待确认记录，编码上限400万字符。同一服务门店桌台最多一个未决命令，即使旧场次或其他员工留下也不自动覆盖。跨进程锁、存储断电恢复、应用卸载/硬件密钥丢失恢复不在本轮验证范围。
- recoverOrder 默认只查1913；not_observed保留原命令。只有明确 retryOriginal 才原样调用1912。传输异常不会自动重发或清理。
- cancelOrder 必须明确确认，只调用1914原作用域；confirmed代表已成单，不声称取消。cancelled才能标记原请求永久终止。该接口不是退单/退款/库存回补。
- 回执逐项校验原请求号、归属、场次、消费会员、金额、币种、付款模式与初始库存状态。confirmed不等于paid。匹配的确认/取消终态才移除对应记录；not_observed、坏回执和别的命令不能移除。
- 控制器串行订单操作，提交/恢复前后检查会话版本和到期。注销、换账号、刷新或关闭后的迟到响应不能作为新会话结果展示。默认查回没有业务写入，但服务端会取请求序列锁。

不同员工无法代查本机他人未决请求；管理员接管及跨设备恢复仍待独立授权设计，不绕过当前归属校验。UI需区分“原请求已成单”“原请求已终止”“仍未查到”；错误/网络中断不能显示支付成功。后台支付恢复、会员余额授权、现金确认、第三方核销仍未完成。
