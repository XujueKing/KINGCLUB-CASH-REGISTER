## 3. 身份与权限是接入前置条件

现有认证执行器仅接受 android/ios 客户端类型，登录成功可能通知撤销其他设备会话。不能直接用现有手机账号登录收银机来验证，也不能把收银机伪装成免撤销客户端。

待确认的身份契约：收银设备绑定门店、当班员工身份、班次及审计归属；不与会员手机会话互相挤下线。需要明确采用专用员工账号还是另建员工终端会话授权，未经确认不修改现有注册/登录流程、不授予任何真实账号权限。

客户端门店选择仅为请求条件，服务端必须重新验证授权。不得允许输入 storeRef 即跨店访问。负责人或超级管理员的既有能力不能自动当作一般收银员权限。

## 4. 第一阶段建议：只读工作台

这是建议范围，尚未完成 UI 设计批准或应用实现：

1. 环境连接检查：分别配置登录与商务入口，展示网络状态；不把服务健康等同于登录成功或营业可用。
2. 经批准的员工/设备认证与门店选择：复用服务端授权结果，切换身份立即清空缓存，迟到响应不得污染新会话。
3. 桌台档案列表：分页、服务端营业日、启停用状态；未经实时场次查询不生成占桌状态。
4. 桌台当前场次与订单只读明细：先补齐员工门店授权查询，再展示真实明细。待付款、已付款与已上菜分开建模。

收钱吧截图作为横屏触控流程参考：桌台网格、分类商品、订单侧栏、结账明细、订单查询、交班和报表。截图中的改价、免单、赠品、挂账、转并桌等均不自动成为获准接入的能力。

后续写操作顺序建议：员工开台与入座 → 代点/APP 同场次订单汇总 → 出品与已上 → 结算 → 清台 → 打印/交班。每步单独完成接口评审与验证，不把前后付费、AA、券或存酒规则合并成一个简单支付状态。

## 5. 数据与一致性约束

- 复用门店、桌台、tableSessionRef 和服务端订单；桌号不作为全平台唯一键。二维码不代表入座或付款授权。
- 开台快照先付/后付模式；不能因门店后来改配置改变已成立场次。AA 保持已确认的全付齐规则。
- 服务端计算价格、核验付款、处理预留和出库；客户端不能上报“已付”改变账务。
- 重试保留原幂等键；支付未知不创建第二张订单，先查询原订单。
- 清台关闭场次但保留订单、支付、上菜和审计历史，新轮次必须用新场次。
- 暂不承诺商务 WebSocket 实时同步；需要先核对专用事件和授权范围。若先用轮询，须限定门店、频率和前台生命周期，并展示数据更新时间。
- 离线只读缓存要明确过期，写操作只保存草稿，不伪造库存/订单确认。
- 不直连数据库，不复用物业接口权限，不复制手机登录凭据。
